# Разработка TGUI в браузере

`tgui-preview` открывает настоящие интерфейсы текущего checkout с тестовыми
данными в обычном браузере, без запуска BYOND и входа в игру. Он собирает основной
TGUI в `tgui/public/.tmp/preview`, следит за изменениями исходников и обновляет
preview. Стандартные Font Awesome и tgfont загружаются из checkout. Каталог данных и cache BYOND не используются.

## Запуск

Из корня checkout:

```powershell
bin/tgui-preview.cmd
# Или через штатный pipeline, с другим портом при необходимости:
tools/build/build.bat tgui-preview --port=5173
```

При уже установленных зависимостях и собранном `tgfont` из `tgui/`: `bun tgui:preview`. Для чистого checkout используйте штатный pipeline выше: он также собирает шрифт tgfont.
Дождитесь успешной сборки и откройте
[локальную панель](http://127.0.0.1:5173/). Остановить свой сервер можно через
`Ctrl+C`. Preview слушает только loopback.

Выберите интерфейс и fixture, задайте размеры iframe, отредактируйте JSON и
нажмите `Apply`. Например:

- [Radio](http://127.0.0.1:5173/?interface=Radio&fixture=radio) — частота и кнопки радио.
- [AirAlarm](http://127.0.0.1:5173/?interface=AirAlarm&fixture=air-alarm) — показания,
  страницы управления и статические настройки порогов. Fixture намеренно содержит
  только два порога, два режима и пустые списки устройств.

Любой найденный интерфейс можно выбрать по имени, но для его отображения нужны
подходящие данные. Выбор имени сам по себе не создаёт данные его игрового объекта.

## Данные и действия

JSON имеет форму штатного TGUI update:

```json
{
  "config": {
    "interface": { "name": "Radio" },
    "title": "Handheld Radio",
    "window": { "size": [330, 210] }
  },
  "data": {},
  "static_data": {},
  "shared": {}
}
```

Это схема сообщения, а не готовая fixture Radio: обязательные поля `data` нужно
взять из его контракта. Preview дополняет служебные поля `config` значениями по
умолчанию. `data` соответствует DM `ui_data`, `static_data` — `ui_static_data`.
Фронтенд получает их через штатный backend. В `shared` значения кодируются
строками JSON, как в native transport; для большинства начальных состояний
достаточно `{}`.

Перед подготовкой состояния прочитайте компонент в `packages/tgui/interfaces/`,
его дочерние компоненты и реальные DM `ui_data`, `ui_static_data`, `ui_act`.
Сохраните различия между `null`, `0`, пустой строкой, списком и объектом;
передайте обязательные поля, корректные идентификаторы и согласованные флаги.
Встроенные примеры лежат в
`packages/tgui-dev-server/preview/fixtures/`. Новая fixture — JSON с тем же
контрактом, без копирования DM-алгоритмов в JavaScript.

Исходящие `act()` записываются в журнал действий с именем и параметрами.
Preview не выполняет DM `ui_act` и не имитирует его бизнес-логику. Например,
нажатие кнопки радио запишет запрос, но серверный флаг не переключится.
Для следующего серверного состояния измените JSON и снова нажмите `Apply`.
Локальные состояния React работают в браузере. Для `useSharedState` preview возвращает локальный ответ с новым значением, чтобы переключались страницы и фильтры; это имитация UI-транспорта. Клиентское хранилище держится в памяти iframe и очищается при `Apply` и пересборке.

Не переносите в fixture реальные персональные данные, секреты или содержимое
пользовательских runtime-сохранений. Используйте вымышленные значения и refs.

## Рабочий цикл и проверки

1. Проследите DM-контракт, компонент и действия. Переиспользуйте существующие
   компоненты, стили и точки композиции. [Каталог tgui-core](https://tgstation.github.io/tgui-core/)
   показывает отдельные компоненты; preview показывает полные локальные интерфейсы.
2. Подготовьте состояния по риску изменения: обычное, пустое, заблокированное,
   длинные строки или крайние значения. Проверьте реальный размер окна, прокрутку,
   читаемость и журнал действий. Сохраните кадр и использованную fixture в evidence.
3. Для обоснованного риска используйте существующие frontend-тесты. Текущий runner —
   Bun с Happy DOM и React Testing Library (`bunfig.toml`, `happydom.ts`,
   `packages/tgui/__mocks__/`); раздел о Jest в `writing-tests.md` устарел.
   Эти mocks тоже не исполняют DM.
4. Перед PR выполните `bin/tgui-build.cmd`: сборку, Biome lint, TypeScript и тесты.
   `bun tgui:build` отдельно выполняет только сборку. Выполните также обязательные
   проверки проекта, включая DreamChecker, по корневому `AGENTS.md`.

Отдельные проверки из корня: `tools/build/build.bat tgui`, `tgui-lint`,
`tgui-tsc`, `tgui-test` — каждый target передаётся после `build.bat`.
При прямом запуске Bun команды `tgui:build`, `tgui:tsc`, `tgui:test` выполняются
из `tgui/`, а `bun tgui:lint` — из корня. Lint не исправляет код автоматически.

Для проверки с реальным игровым клиентом существует `bin/tgui-dev.cmd`
(`--reload` для разового обновления cache, `--debug` для логов). Этот watcher
обновляет BYOND cache и клиент через link; он требует игрового контекста для
проверки настоящих данных и действий.

## Границы preview

Fixture проверяет отображение переданных данных, локальные взаимодействия и
исходящие запросы. Она не подтверждает серверные права, повторную валидацию,
таймеры, расход ресурсов, обработку объектов и cleanup. Для этих изменений нужны
относящиеся DM-тесты или точный сценарий в игре.

Игровые assets, динамические иконки и ресурсы, выдаваемые сервером по refs, могут
отсутствовать в обычном браузере. Native API BYOND, игровые карты, вывод в
клиентские окна и другие клиентские возможности не воспроизводятся полностью.
Если интерфейсу нужны такие данные или API, обозначьте пробел проверки и
проверьте соответствующее поведение в BYOND. Успешный браузерный кадр не является
проверкой DM runtime или полной совместимости с игровым WebView.
